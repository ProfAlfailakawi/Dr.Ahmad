# Archive 2036 — scalability contract

This is an internal architecture contract. It must not create a new public UI or change the editorial visual language.

## Capacity target

The public site must remain usable as the archive grows beyond the current corpus, with an operational target of at least:

- 5,000+ articles
- 1,000+ media appearances
- hundreds to thousands of research records/books
- 100,000 metadata records in indexing/build stress tests

The 100k target is a guardrail for data structures and build algorithms, not a requirement to render 100,000 DOM nodes on one page.

## Non-negotiable rules

1. **Never build all-pairs similarity in the browser or build pipeline.** Candidate generation must use inverted postings / bounded neighborhoods and a hard per-node neighbor cap.
2. **Never download the full article-body archive to open one article.** Bodies are stable-hash sharded at build time; public readers load one shard with a legacy fallback for development/admin tools.
3. **Public Firestore is a live delta, not the durable archive.** Public bootstrap reads a bounded recent window; deployments bake the durable archive into the site snapshot. Admin realtime behavior stays separate.
4. **List pages render bounded pages/slices.** Filters may operate on metadata, but the DOM must not grow with the full archive.
5. **Search uses postings/candidate narrowing before ranking.** A query must not normalize and score every body on every keystroke. Article search and the cross-type knowledge graph must not duplicate the same large corpus in memory.
6. **Knowledge graph, Concept Weave and media moments cache immutable indexes.** Repeated interaction reuses the same postings instead of rebuilding them.
7. **Structured data is bounded.** Collection JSON-LD reports the true count but does not serialize the full archive into one page.
8. **Large visual maps use level of detail (LOD).** Never render the whole archive as DOM/SVG nodes. Keep a deterministic, category/year-balanced visual sample; pin direct-entry, latest, managed, reader-journey and active-query stars; remove per-item continuous motion and skip heavyweight global relation files at scale.
9. **Sitemaps scale with the archive.** Above 45,000 indexable URLs, `sitemap.xml` becomes an index and content URLs are split into bounded child sitemaps.
10. **Generated shards are build artifacts.** `public/archive/bodies/` is regenerated by the build and is not committed.
11. **Regression is blocked in CI.** `archive:guard` protects architectural invariants and `archive:scale:self-test` exercises 100,000 synthetic records.

## Commands

```bash
npm run archive:guard
npm run archive:scale:self-test
npm run archive:shards
```

The scale self-test enforces upper bounds for indexing, faceted queries, posting-list search, bounded similarity construction and retained heap growth. Thresholds are deliberately generous enough for CI variance but tight enough to catch accidental O(n²) regressions.

## Visual rule

Archive 2036 is intentionally invisible to visitors. It is an engineering layer beneath the existing editorial design. Scaling must remove latency and hidden work, not add dashboards, badges, loaders, counters, or visual clutter.
