## السبب الجذري المثبت من المصدر

### السبب المباشر
GitHub `workflow_dispatch` يقبل الطلب غالبًا بـ HTTP 204 من دون جسم أو `run_id`. الكود كان يقبل الاستجابة لكنه لا يملك آلية موثوقة لربط الطلب بالتشغيل الناشئ، بينما واجهة الحالة تعتمد على حقول تشغيل قد تبقى فارغة.

### السبب الجذري
مسار الإنتاج كان يملك محرك استئناف وجودة جيدًا، لكن طبقة المراقبة بين dispatch وFirestore لم تكن تسجل كل مرحلة، ولا تحفظ step/job/errorCode/current/total. لذلك أي فشل في سر، TTS، FFmpeg، البوابة، الرفع أو مزامنة Firestore يظهر كـ `needs_review` ورسالة عامة مستخرجة متأخرًا من audit إن وجد.

### الإصلاح
- تحديث مرحلي واضح من GitHub Actions إلى Firestore.
- حفظ run ID ورابط التشغيل من بيئة Actions نفسها، وهي المصدر الموثوق.
- حفظ المرحلة، المقطع الحالي، الإجمالي، آخر ملف، بدء الدمج، الرفع، رمز الخطأ وعدد المحاولات.
- `stageHistory` غير هدّام لعرض التسلسل.
- الاستئناف الموجود في المحرك لم يُلغَ؛ الملفات المكتملة ذات hash نفسه تبقى قابلة لإعادة الاستخدام.

### ما لم يتغير
الحوار اليدوي لم يُعدّل أو يولّد أو يعاد صياغته. لم تُضف Gemini أو OpenAI، وبقي `--manual-exact --no-gemini` وإثبات التطابق قبل النشر.

## مجموعات البيانات
- `analytics_events`: أحداث عامة مجهولة، قراءة أدمن فقط، كتابة خادم فقط.
- `admin_tool_events`: أحداث دلالية خاصة بالأدمن، قراءة/كتابة أدمن فقط.
- `podcast_production`: أضيفت حقول stage/status/history/progress/run URL؛ لا تغيير في نص الحوار.
- لا يلزم composite index للاستعلامات الحالية لأنها تعتمد على حقل تاريخ واحد؛ فهارس الحقول المفردة التلقائية تكفي.

## حدود الإثبات
لم تتوفر بيانات Firestore الحية ولا سجل GitHub للحلقة المتوقفة داخل الحزمة؛ لذلك تم إثبات الخلل البنيوي من المصدر، لا الادعاء بتحديد رقم المداخلة الحية المتوقفة. بعد النشر ستعرض الحقول الجديدة النقطة الدقيقة في التشغيل التالي أو إعادة المحاولة.
